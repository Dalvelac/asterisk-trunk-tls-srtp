Asterisk Trunk with TLS and SRTP Support

What does encryption add to a voice call? Two Asterisk servers exchanged the same pair of tones while tcpdump recorded the signaling and every audio packet on their trunk.

View measurementsExplore the setup

+5% steady-media bandwidth. The combined IPv4 rate averaged 160 kb/s with RTP and 168 kb/s with SRTP.

What the trunk protects

Introduction

A private branch exchange (PBX) routes telephone calls. A trunk carries calls between exchanges. Here A dials extension 200 on B. SIP sets up the call, SDP describes the codec and listening ports, and RTP sends the sound in small UDP packets. The secure profile wraps SIP in TLS and protects the audio with SRTP. Each flow has its own evidence and bandwidth cost. SIP and SDP standards

Current practice

Asterisk’s PJSIP channel driver supports both SDES and DTLS media keying. SDES carries SRTP keys inside the SDP offer and answer, making authenticated, confidential signaling essential. The laboratory uses this approach on a single trusted PBX-to-PBX hop. Browser-based WebRTC uses DTLS-SRTP for media key establishment. The choice of keying method affects what a packet trace can establish. Asterisk, RFC 4568, RFC 8827

The profile pins TLS 1.2 so that each measured connection uses the same handshake. Current IETF guidance encourages TLS 1.3 when both sides support it. A different TLS version, certificate chain or session-resumption policy would merit a new setup measurement. RFC 9325

Trunk setup

Both ends run Asterisk certified-22.8-cert5 on the same isolated Docker bridge. The two modes share the codec, dialplan and media path.

Baseline trunk

work/profiles/plain.conf 
[link]
type=transport
protocol=tcp
bind=@LOCAL_IP@:5060

[media-policy](!)
media_encryption=no

Port 5060 carries a readable SIP conversation. The SDP answer identifies the receiver’s audio port. Capturing plain RTP allows playback of each tone.

Secure trunk

work/profiles/secure.conf 
[link]
type=transport
protocol=tls
bind=@LOCAL_IP@:5061
method=tlsv1_2
verify_server=yes
verify_client=yes
require_client_cert=yes

[media-policy](!)
media_encryption=sdes
srtp_tag_32=no

Port 5061 carries TLS. SDES supplies the keys for SRTP through the protected SDP conversation. The shared endpoint sets media_encryption_optimistic=no to require the selected protection.

Place the call

The launcher originates PJSIP/200@peer on A. B matches A’s source address, enters its from-peer dialplan and answers. Each side starts a tone with PlayTones. The common endpoint selects ulaw:20 and direct_media=no. Asterisk records the Call-ID, codec, active security flags and media counters on both channels. Both PBXs loaded chan_pjsip, res_pjsip_sdp_rtp and res_srtp. PJPROJECT 2.15.1 reported PJ_HAS_SSL_SOCK=1 in its build options.

Authenticate the peers

A validates B’s certificate chain and the DNS name it dialed. B requires a valid client certificate from the lab CA. After the handshake, B maps A’s source IP to the PJSIP endpoint. Both certificates permit client and server use. This trust boundary contains only the two lab nodes.

The TLS control verified B’s DNS name using A’s client identity. B rejected a client that omitted its certificate. Together with the certificate request and exchange in the captured calls, this confirms mutual TLS on the trunk. When A contacted B at its correct IP under the alternate name pbx-b, A rejected the server identity. Certificate checks.

Measurement method

One accounting layer and two explicit time intervals make the comparison repeatable.

  1. Recreate the connection. Start both PBXs fresh, attach tcpdump to A’s eth0, then place one A-to-B call. On each PBX the recorder sets AFTER_CHECK_SECONDS=60. The dialplan already waits two seconds before its channel reading, giving approximately 62 seconds of answered audio in each run.
  2. Count cold signaling. Start at A’s first TCP SYN and stop just before the first confirmed audio packet in either direction. Sum ip.len for the call’s TCP stream in that interval, including TCP acknowledgments and retransmissions. A common boundary works even when TLS hides the SIP answer.
  3. Count steady media. Using the first audio packet as the observable origin M, take [M + 5 s, M + 55 s). Match the actual two UDP endpoints in both directions. Exclude the neighboring RTCP or SRTCP ports and all TCP signaling. M follows answer in this dialplan. It is a capture-based proxy for the answer time.

IPv4 accounting

ip.len is the IPv4 total length in bytes. It includes IP, transport and media headers plus payload. Ethernet framing, preamble and link idle time lie outside the accounting layer. The mode comparison reports the observed load at this virtual network interface. IPv4 total length

Mean kb/s = 8 × Σ IP bytes ÷ 50 seconds ÷ 1,000

Packets/s uses the 50-second interval. Typical size is the median IPv4 packet length in the selected direction and window. The combined row adds both directions. Setup is a byte count per new call, so it stays separate from steady bitrate.

From samples to packet length

The visible RTP timestamps advance by 160 ticks per consecutive packet in the steady streams. G.711 µ-law uses an 8 kHz clock and one byte per sample. This gives 160 bytes of sound per 20 ms packet, or 50 packets per second. The header audit found a 20-byte IPv4 header, 8-byte UDP header and 12-byte RTP header. RTP and audio profile.

Baseline prediction, one direction
(160 + 20 + 8 + 12) bytes × 8 × 50 = 80,000 bit/s.

A separate answered diagnostic call on the same build and configuration reported AES_CM_128_HMAC_SHA1_80 after libSRTP installed the stream policies. AES counter mode encrypts the payload without expanding it, and the HMAC-SHA1 authentication tag adds 80 bits (10 bytes) per RTP packet. All measured secure audio packets were 210 IPv4 bytes in the selected windows. The diagnostic establishes the profile for that configuration. The timed calls supply the independent wire-length and channel evidence. Installed policy parameters, SDES protection profiles.

Secure prediction, one direction
(200 + 10) bytes × 8 × 50 = 84,000 bit/s. Across both directions the predicted increase is 8 kb/s.

Assessment and conclusion

Contribution

The two-mode trunk, matched call generator and packet accounting script form a repeatable test. Another student can inspect the IP length of an individual packet, trace its port pair to a specific call, and recompute each published row. Checking the active media flag alongside the TLS handshake resolves an ambiguity that a signaling screenshot alone would leave open.

Where the result applies

The steady-media result belongs to this codec, packet interval, IP version and SRTP negotiation. A smaller packet interval spreads the same duration of sound across more authenticated packets. Cold setup also depends on handshake flights, certificates, TCP segmentation and call headers. This experiment changed TLS signaling and SDES media negotiation together. The cold byte difference therefore includes both effects and their TCP acknowledgments.

All calls shared a quiet virtual bridge on one host. The sample captures variation under these conditions and provides no estimate of WAN jitter, carrier loss, CPU cost or user-perceived voice quality. A long-lived trunk could reuse its TLS connection across calls and incur the full handshake less often.

Conclusion

Securing this trunk changed the combined steady rate by +8 kb/s (+5%). Cold setup averaged 3,127 IPv4 bytes in the baseline and 8,054 with TLS and SDES, a change of +4,927 bytes (+157.563%). For a full-duplex link carrying this codec, start the media budget at 84 kb/s per active call in each direction. Allow additional capacity for control packets and link framing. Estimate cold setup from the number of new connections the trunk actually opens.
